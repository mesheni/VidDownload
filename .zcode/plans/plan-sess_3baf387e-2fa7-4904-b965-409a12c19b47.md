# План: исправление багов + улучшения VidDownload (v0.7.1 → v0.8.0)

## Итоги анализа (все находки проверены по коду)

### Критические
1. **Самообновление приложения сломано**: CI публикует только `VidDownload.msi`, `UpdateService.CheckAppUpdateAsync` (UpdateService.cs:124-125) принимает .msi-asset, а `MainViewModel.UpdateAppAsync` (MainViewModel.cs:646) жёстко кодирует путь `...\VidDownload.WPF.exe` → Updater не находит файл, но `Application.Current.Shutdown()` (строка 660) уже выполнен — приложение закрывается и не перезапускается.
2. **Нет проверки HTTP-статуса при скачивании** (UpdateService.cs:73, 167; FFmpegService.cs:164): при 404/403 HTML-страница ошибки записывается вместо yt-dlp.exe / обновления приложения, затем Updater может затереть рабочий .exe мусором.
3. **Прогресс-бар сбрасывается в 0%**: `ParseLog.ParseProgressLine` (ParseLog.cs:44-51) для любой нераспарсенной строки возвращает `Percent = 0` — строки `at Unknown B/s`, `ETA Unknown`, финальная `100% of X in 00:00:10`, `[Merger]...` роняют бар в ноль прямо во время загрузки. Плюс `(int)percent` усекает 99.9 → 99.

### Высокие
4. `MainViewModel.cs:356` — `Process.Start("explorer.exe", "/open, \"" + _savePath)` — нет закрывающей кавычки: пути с пробелами не открываются.
5. Сравнение версий yt-dlp склеиванием цифр (UpdateService.cs:55-60) — ломается на суффиксах (`-rc1` → всегда «доступно обновление») и несовпадающей длине сегментов.
6. Гонка состояния `IsDownloading`: `CheckUpdateAsync` (MainViewModel.cs:549-571) использует/сбрасывает общий флаг загрузки во время автообновления yt-dlp при старте, ломая состояние активной загрузки пользователя.

### Средние
7. Лог-файл с точностью до секунды + `FileMode.CreateNew` (YtDlpService.cs:24-25, 45) — IOException при повторной загрузке в ту же секунду.
8. `HttpClient` создаётся/диспозится на каждый вызов (UpdateService, FFmpegService) — истощение сокетов; и дублирующиеся проверки интернета на устаревшем `HttpWebRequest` с разными таймаутами.
9. Неатомарная запись settings.json / download-history.json (`File.WriteAllTextAsync` напрямую) + пустые `catch` — сбой/краш = потеря всех настроек или истории без диагностики.
10. Нет обработки закрытия приложения при активной загрузке (осиротевшие процессы yt-dlp, нет подтверждения).
11. `FFmpegService.GetVersionFromProcessAsync` — чтение одной строки + WaitForExit: потенциальный дедлок пайпа.
12. `LoadSettingsAsync` без try/catch запускается fire-and-forget из конструктора (MainViewModel.cs:175, 383-421).
13. Статический `_codecList` наполняется в конструкторе transient-VM (MainViewModel.cs:21, 168-171).
14. История хранит URL вместо названия видео; `FilePath` никогда не заполняется.
15. `Kill` после проверки `HasExited` — TOCTOU (YtDlpService.cs:82-87).

### Низкие
16. Мёртвый код `latestVer` (UpdateService.cs:138); неиспользуемый `ParseLog.Parse`; `async void OnDownloadAgain` без await; неиспользуемый пакет `Xabe.FFmpeg.Downloader`; мусор `<Folder Include="bin\Release\netcoreapp3.1\">` в csproj; Updater не удаляет temp-файл.

### UX/UI
17. **Папку скачивания нельзя изменить из UI** (`_savePath` только из settings.json).
18. После каждой загрузки стираются URL и все выбранные настройки (MainViewModel.cs:318-323) — при ошибке теряется ссылка для правки.
19. Нет Enter для старта, placeholder у поля URL, уведомлений о завершении/ошибке, подтверждения при закрытии с активной загрузкой.
20. Белый комбобокс языка субтитров ломает тёмную тему (MainWindow.xaml:60); шрифт Raleway один раз (строка 44); непереведённый `Content="VidDownload:"` (строка 99); HelpWindow не переключает язык (x:Static вместо динамических биндингов).
21. Одна загрузка за раз — нет очереди, паузы/резюма, трея, мониторинга буфера обмена, лимита скорости.

## Реализация

### Фаза 1 — критические баги
- **UpdateService.cs**: asset-поиск предпочитает `.exe` (MSI игнорируется для самообновления); `DownloadAppUpdateAsync` возвращает фактический путь скачанного файла; проверка `response.IsSuccessStatusCode` во всех 3 местах скачивания (UpdateService ×2, FFmpegService ×1) + скачивание во временный файл с последующей заменой (чтобы сбой не портил существующий yt-dlp.exe).
- **MainViewModel.UpdateAppAsync**: использует путь из `DownloadAppUpdateAsync`; если .exe-asset в релизе нет — сообщение «обновление недоступно, скачайте с GitHub» + открытие страницы релиза (graceful fallback), приложение не закрывается.
- **Updater/Program.cs**: проверка что src — валидный PE (сигнатура `MZ`) перед копированием; удаление temp-файла после успешной замены.
- **ParseLog.cs**: опциональные группы (speed/ETA могут быть `Unknown`), матчинг финальной строки `100% of X in HH:MM:SS at ...`; fallback сохраняет последний известный процент (передаётся последним параметром), а не 0; `Math.Round` вместо усечения.
- **MainViewModel.cs:356**: `Process.Start("explorer.exe", $"\"{_savePath}\"")`.

### Фаза 2 — остальные баги (надёжность)
- **YtDlpService.cs**: уникальное имя лога (ммс+счётчик при коллизии, `FileMode.Create`); `Kill(true)` без `HasExited`-проверки в try/catch; парсинг `[download] Destination: <path>` → проброс названия/пути файла наверх через DownloadProgress для истории.
- **UpdateService.cs / FFmpegService.cs**: общий статический `HttpClient`; одна общая проверка интернета на HttpClient (HTTPS, единый таймаут 5с) — удалить обе HttpWebRequest-копии; корректное сравнение версий yt-dlp посегментно (числовой parse каждой части, суффиксы после `-` игнорируются); удалить мёртвый `latestVer`.
- **JsonSettingsService / JsonDownloadHistoryService**: атомарная запись (temp + `File.Move(..., overwrite)`), ошибки логируются в `%LocalAppData%/VidDownload/logs/`, а не глотаются.
- **MainViewModel**: fire-and-forget обёрнут в safe-хелпер с логированием; `_codecList` → `Codecs.Contains(...)` (удалить статику); разделение состояний — автообновление yt-dlp/FFmpeg больше не трогает `IsDownloading`, а использует свои статусные свойства; после загрузки НЕ сбрасывать выбранные разрешение/кодек/формат; URL очищать только при успехе (при ошибке/отмене оставить для правки).
- **App.xaml.cs / MainWindow**: `OnExit` — отмена активных загрузок (kill процессов) через менеджер очереди; при закрытии окна с активной загрузкой — подтверждение (после появления трея в Фазе 4 — сворачивание в трей по настройке).
- **FFmpegService**: чтение всего stdout (`ReadToEndAsync`) перед ожиданием выхода — устранение риска дедлока.
- **Мелочи**: убрать `async` у `OnDownloadAgain`; удалить неиспользуемый `ParseLog.Parse`; убрать пакет `Xabe.FFmpeg.Downloader` и stale-папку из csproj.

### Фаза 3 — быстрые UX-улучшения
- **Выбор папки**: TextBox с текущим путем + кнопка «Обзор» (FolderBrowserDialog через `System.Windows.Forms`/Ookii или `OpenFolderDialog` из WPF — в .NET 10 доступен `Microsoft.Win32.OpenFolderDialog`), путь персистится в settings.
- **Enter** в поле URL = начать загрузку (KeyBinding → DownloadCommand); Esc = отмена активной.
- **Уведомления**: HandyControl `Growl` о завершении/ошибке каждой загрузки + всплывающее уведомление трея (Фаза 4).
- **Поле URL**: placeholder «Вставьте ссылку...», мягкая валидация (`Uri.TryCreate` http/https или `ytsearch:` — иначе предупреждение, но с возможностью продолжить).
- **Тема/шрифты**: тёмный скин для комбобокса субтитров, Cascadia Code везде, локализация «VidDownload:», HelpWindow перевести на динамические `LocalizedStrings`-биндинги.
- **Лимит скорости**: настройка «Ограничить скорость» (свободный текст, напр. «5M») → `--limit-rate` в Command.cs; UI-поле + персист.
- **Тултипы/AutomationProperties** для основных кнопок; пустое состояние списка очереди («Очередь пуста — вставьте ссылку»).
- Все новые строки — в 3 resx (RU/EN/ZH-CN).

### Фаза 4 — крупные функции
- **Архитектура очереди** (ядро фазы):
  - `Models/DownloadItem.cs`: Id, Url, Title, FilePath, снимок настроек (Settings), статус (Queued/Downloading/Paused/Completed/Failed/Cancelled), прогресс (percent/speed/eta/size/status), CTS.
  - `Services/DownloadQueueService.cs`: `ObservableCollection<DownloadItem>`, последовательное выполнение (SemaphoreSlim с настраиваемым максимумом параллельных, по умолчанию 1), команды Add/Cancel/Remove/ClearFinished/Pause/Resume, события ItemCompleted/ItemFailed для уведомлений. Использует `YtDlpService.DownloadAsync` без изменений (по процессу на элемент).
  - `MainViewModel` упрощается: URL + опции → добавление в очередь; кнопка «Скачать» = «добавить и запустить»; общий прогресс активного элемента в существующем прогресс-баре.
- **UI очереди**: список в MainWindow (ListView с колонками: название/URL, прогресс, скорость, статус, кнопки пауза/отмена/удалить/открыть папку); окно становится `CanResize` с MinWidth/MinHeight, список растягивается.
- **Пауза/резюме**: Pause = kill процесса с флагом PauseRequested (статус Paused, .part-файл остаётся), Resume = перезапуск той же команды — yt-dlp продолжает докачку нативно.
- **Трей**: пакет `H.NotifyIcon.Wpf`; иконка из icon.ico; меню (Показать/Пауза всех/Открыть папку загрузок/Выход); настройка «Сворачивать в трей при закрытии»; balloon-уведомления о завершении/ошибке (замена Growl при свёрнутом окне).
- **Мониторинг буфера обмена**: переключатель (персистится); DispatcherTimer ~1с; новая http(s)-ссылка ≠ предыдущая → Growl «Добавить в очередь?» с кнопкой (авто-скрытие 6с); ошибки доступа к буферу (COMException) молча пропускаются.
- **История**: реальный Title и FilePath из парсинга `Destination:`; кнопка «Повторить» кладёт URL в поле/очередь.

### Фаза 5 — CI (portable .exe в релизе)
- `.github/workflows/build-and-installer.yml`: доп. шаг — `dotnet publish VidDownload.WPF -c Release -r win-x64 --self-contained true /p:PublishSingleFile=true` + Updater.exe рядом; загрузить `VidDownload.exe` (и Updater.exe) в Release рядом с MSI. Asset-паттерн приложения уже ищет `.exe` (Фаза 1).

### Фаза 6 — тесты, сборка, документация
- Новый тест-проект `VidDownload.Tests` (xunit): ParseLog (все форматы строк yt-dlp, сохранение процента, 100%), сравнение версий, Command.cs (наборы аргументов для видео/аудио/плейлист/лимит скорости), DownloadQueueService state machine (с моком IYtDlpService).
- `dotnet build` + `dotnet test` зелёные; ручная проверка: загрузка/отмена/пауза, смена языка, открытие папки с пробелами в пути.

## Порядок и риски
Фазы 1-3 не меняют архитектуру — безопасно. Фаза 4 — крупнейшая: очередь вводится так, что текущий сценарий «одна загрузка» остаётся рабочим частным случаем очереди. Новые NuGet: `H.NotifyIcon.Wpf`, `xunit` (тесты).
